# Metodología y Fundamentos de Testing (ISTQB)

### 1. Aplicación de los 7 Principios de Testing
* **Pruebas tempranas (Shift-Left):** Diseñar las pruebas antes de la implementación de código para detectar fallas conceptuales en la fase de especificación.
* **Pruebas exhaustivas imposibles:** Aplicar técnicas formales de muestreo representativo en lugar de combinatorias infinitas.
* **Agrupación de defectos (Defect Clustering):** Concentrar mayor densidad de pruebas en las áreas identificadas con mayor riesgo funcional y técnico.
* **Paradoja del pesticida:** Variar los conjuntos de datos de prueba y combinaciones en los esquemas de escenario para evitar que las pruebas pierdan efectividad.
* **Las pruebas demuestran la presencia de defectos, no su ausencia:** Asegurar aserciones contundentes y verificables.
* **Las pruebas dependen del contexto:** Diseñar pruebas alineadas a la naturaleza de la arquitectura (Web UI, API, integración).
* **Falacia de ausencia de errores:** Validar no solo que el sistema no falle sintácticamente, sino que resuelva la necesidad de negocio del usuario.

### 2. Técnicas de Diseño de Pruebas de Caja Negra (Obligatorias)
Cada caso de prueba diseñado debe explicitar la técnica formal utilizada:
* **Partición de Equivalencia (EP):** Identificación de clases de equivalencia válidas (comportamiento esperado) e inválidas (rechazo controlado).
* **Análisis de Valores Límite (BVA):** Cobertura rigurosa en fronteras: mínimo, máximo, nominal y valores adyacentes inválidos (ej. longitudes de strings, rangos numéricos).
* **Tablas de Decisión (Decision Tables):** Modelado de combinaciones complejas de condiciones booleanas, dependencias entre campos y reglas de negocio multi-variable.
* **Transición de Estados:** Verificación de cambios de estado en el ciclo de vida del dato o sesión (ej. usuario no registrado -> cuenta activa -> login exitoso).
* **Ataque de Errores y Casos Borde (Error Guessing / Edge Cases):** Derivación de escenarios negativos guiados por la Matriz de Riesgos (caracteres especiales no contemplados, inyección de scripts, campos vacíos, timeouts).

### 3. Niveles y Tipos de Prueba
* **Niveles:** Pruebas de Sistema (End-to-End en Web UI) y Pruebas de Aceptación (UAT BDD).
* **Tipos:**
  * Pruebas Funcionales: Flujo principal (Happy Path), flujos alternos y flujos de excepción/negativos.
  * Pruebas No Funcionales básicas aplicables al formulario: Usabilidad visual, accesibilidad básica de controles y sanitización de seguridad de entradas.

# Estándares de Redacción Cucumber / Gherkin

1. **Idioma Oficial:** Español formal estandarizado (`Característica`, `Regla`, `Antecedentes`, `Escenario`, `Esquema del escenario`, `Ejemplos`, `Dado`, `Cuando`, `Y`, `Entonces`).
2. **Estilo Declarativo (Buenas prácticas BDD):**
   * *Correcto:* `Cuando el usuario completa sus credenciales válidas y confirma el registro`
   * *Incorrecto (Imperativo UI frágil):* `Cuando hace clic en el input username, escribe 'user123' y hace clic en el botón con id #submit`
3. **Atomicidad e Independencia:** Cada escenario debe ser completamente autónomo; ningún escenario debe depender de la ejecución o estado generado por otro.
4. **Parametrización Eficiente:** Obligatorio el uso de `Esquema del escenario` con matrices de `Ejemplos` para particiones de equivalencia y análisis de valores límite.
5. **Taxonomía de Tags / Etiquetas:**
   * `@web` (nivel de ejecución)
   * `@smoke` (flujos críticos del camino feliz)
   * `@regression` (suite de regresión completa)
   * `@functional` / `@negative` (tipo de prueba)
   * `@{{NOMBRE_FUNCIONALIDAD_MINUSCULAS}}` (tag de feature)

# Reglas de Comportamiento y Restricciones Estrictas

1. **Cero invención (Fidelidad a las fuentes):** No agregues reglas de validación, botones ni endpoints no contemplados en el funcional o diseño acordado.
2. **Protección de Datos Sensibles:** No utilices datos reales, correos de personas reales, contraseñas productivas ni PII. Toda la data de prueba debe ser estrictamente sintética y anonimizada.
3. **Respeto a los Alcances Incluyentes y Excluyentes:** No diseñes casos de prueba para funcionalidades explícitamente excluidas (ej. si el envío de correo de activación o CAPTCHA están fuera de alcance, no crees escenarios que verifiquen esos componentes).
4. **Trazabilidad Total:** Todo escenario de prueba debe estar mapeado contra un Criterio de Aceptación del documento funcional.

# Estructura del Archivo de Salida

El archivo Markdown generado debe contener exactamente las siguientes secciones:

1. **Metadatos del Test Plan** (Proyecto, funcionalidad, versión, fecha, fuentes de verdad consultadas).
2. **Alcance y Objetivos de la Prueba** (Objetivos generales, alcance cubierto, exclusiones explícitas, criterios de entrada y criterios de salida).
3. **Estrategia y Enfoque Metodológico** (Niveles y tipos de prueba aplicados, justificación con base en los 7 principios de testing).
4. **Matriz de Trazabilidad de Requisitos (RTM)** (Tabla con: ID de Caso, Requisito / Criterio de Aceptación, Técnica ISTQB aplicada, Tipo de Prueba, Prioridad MoSCoW [Must/Should/Could/Won't], Identificador de Escenario Gherkin).
5. **Especificación de Casos de Prueba en Gherkin (Cucumber)** (Bloques de código `gherkin` completos, con tags, `Antecedentes`, `Escenario` y `Esquema del escenario` con tablas de `Ejemplos`).
6. **Estrategia y Dataset de Datos de Prueba (Test Data Management)** (Definición de datasets sintéticos válidos e inválidos, reglas de unicidad y generación de datos dinámicos).
7. **Criterios de Suspensión y Reanudación** (Condiciones que detienen la suite de pruebas y condiciones para reactivarla).
