## 3. Estrategia y Técnicas de Diseño de Pruebas (ISTQB)

### 3.1. Niveles y Tipos de Prueba

| Nivel de Prueba | Tipo de Prueba | Herramienta / Framework | Enfoque |
| :--- | :--- | :--- | :--- |
| **Pruebas de Sistema (E2E)** | Funcional (Web UI) | Selenium WebDriver + JUnit 5 | Verificación de interacción en navegador real contra el DOM. |
| **Pruebas de Aceptación** | BDD / Comportamiento | Cucumber (Gherkin en Español) | Especificación ejecutable orientada al valor de negocio. |
| **Pruebas de Integración** | Funcional / HTTP (si aplica) | REST Assured | Validación de endpoints y transporte de datos. |

### 3.2. Aplicación de los 7 Principios de Testing
* **Pruebas tempranas:** Diseño de escenarios BDD previo a la codificación de steps para alinear expectativas de desarrollo y QA.
* **Pruebas exhaustivas imposibles:** Aplicación de técnicas de diseño de caja negra (EP y BVA) para seleccionar subconjuntos óptimos de datos.
* **Agrupación de defectos:** Focalización de pruebas negativas en los puntos críticos de mayor riesgo identificados (ej. unicidad y validación de contraseñas).
* **Paradoja del pesticida:** Variación de datasets dinámicos y sintéticos mediante generadores de datos aleatorios.

### 3.3. Técnicas de Caja Negra Utilizadas por Campo / Flujo

| Elemento / Campo | Técnica ISTQB Aplicada | Clases de Equivalencia / Fronteras Evaluadas |
| :--- | :--- | :--- |
| **[Campo 1, ej: User ID]** | Partición de Equivalencia (EP) + BVA | Válido: Alfanumérico exacto 10 chars.<br>Inválido: < 10 chars, > 10 chars, caracteres especiales. |
| **[Campo 2, ej: Password]** | Tabla de Decisión | Combinaciones de: Mayúscula (V/F), Minúscula (V/F), Número (V/F), Especial (V/F). |
| **[Campo 3, ej: Teléfono]** | Análisis de Valores Límite (BVA) | Fronteras: 8 dígitos (inválido), 9 dígitos (válido), 10 dígitos sin prefijo (inválido). |
| **[Flujo de Duplicidad]** | Ataque de Errores (Error Guessing) | Reutilización de User ID existente variando mayúsculas/minúsculas (insensibilidad). |

## 4. Matriz de Cobertura y Trazabilidad de Requisitos (RTM)

> **Prioridad MoSCoW:**
> * **Must:** Obligatorio para release / bloqueo crítico si falla.
> * **Should:** Alta prioridad; necesario pero no bloquea el release si existe contingencia.
> * **Could:** Deseable / baja prioridad.
> * **Won't:** Pospuesto para fases posteriores.

## 5. Especificación de Casos de Prueba en Gherkin (Cucumber)

> **Ubicación en el proyecto:** `src/test/resources/Feature/[Modulo]/[NombreFeature].feature`

```gherkin
# language: es
@web @[nombre_funcionalidad]
Característica: [Título de la Funcionalidad]
  Como [tipo de usuario o actor]
  Quiero [acción o capacidad que realiza en el sistema]
  Para [beneficio o valor de negocio esperado]

  Antecedentes:
    Dado [precondición común a todos los escenarios, ej. que el usuario navega a la página X]

  @smoke @positive
  Escenario: TC-01 - [Nombre descriptivo del flujo feliz]
    Cuando [acción principal con datos válidos]
    Y [acciones secundarias o selecciones]
    Y confirma la acción haciendo clic en [botón]
    Entonces [resultado esperado positivo observable]
    Y [verificación complementaria de estado o URL]

  @regression @negative
  Escenario: TC-02 - [Nombre del escenario negativo específico]
    Dado [condición previa específica, ej. que ya existe un registro con valor X]
    Cuando [el usuario intenta registrar o enviar el valor duplicado X]
    Y confirma la acción haciendo clic en [botón]
    Entonces [mensaje de error o rechazo del sistema]
    Y [verificación de que el estado no fue alterado o se preservan datos válidos]

  @regression @boundary @negative
  Esquema del escenario: TC-03 - [Validación de valores límite y particiones inválidas]
    Cuando ingresa en el campo "<campo>" el valor "<valor_prueba>"
    Y hace clic en el botón de confirmación
    Entonces el sistema rechaza la solicitud con el mensaje "<mensaje_esperado>"

    Ejemplos:
      | campo    | valor_prueba | mensaje_esperado        |
      | [campo1] | [valor_min]  | [Mensaje error longitud] |
      | [campo1] | [valor_max]  | [Mensaje error formato]  |
      | [campo2] | [valor_inv]  | [Mensaje requerido]     |
```

## 6. Estrategia y Dataset de Datos de Prueba (Test Data Management)

### 6.1. Datasets Sintéticos Estandarizados

| Tipo de Dato | Estrategia de Generación | Ejemplo Sintético | Propósito de Prueba |
| :--- | :--- | :--- | :--- |
| **Identificador Único** | Dinámico con timestamp / random | `U` + 9 alfanuméricos (`U8kL29aX1z`) | Evitar colisiones de clave primaria. |
| **Contraseña Válida** | Compleja fija o parametrizada | `TestPass#2026!` | Cumplir política de robustez. |
| **Correo Electrónico** | Sintético con dominio de prueba | `qa.test.{timestamp}@petstore.mock` | Garantizar unicidad en cada ciclo. |
| **Valores Límite** | Strings calibrados por longitud | Longitudes exactas 9, 10 y 11 caracteres | Probar fronteras de validación. |

### 6.2. Reglas de Aislamiento y Limpieza
* **Independencia de datos:** Ningún caso debe depender de datos creados en ejecuciones manuales previas.
* **Nomenclatura controlada:** Utilizar siempre prefijos identificables (ej. `QA_AUTO_`) para facilitar auditorías o limpiezas periódicas en la base de datos.

## 7. Criterios de Suspensión y Reanudación

### 7.1. Criterios de Suspensión
La ejecución de la suite de pruebas se suspenderá inmediatamente si se presenta alguna de las siguientes condiciones:
1. El ambiente de pruebas (URL base) está caído o retorna error HTTP 500/503 persistente en el inicio.
2. Un defecto bloqueante en el formulario impide la carga de los componentes principales (DOM inaccesible).
3. Más del 30% de los casos automatizados de la suite `@smoke` fallan por problemas de infraestructura o selectores.

### 7.2. Criterios de Reanudación
Las pruebas se reanudarán cuando:
1. El equipo de DevOps/Desarrollo confirme la estabilidad del entorno y la resolución del incidente.
2. Se realice un smoke test exploratorio manual de 1 caso exitoso previo al relanzamiento de la suite automatizada.

---

## 8. Criterios de Aceptación y Aprobación de la Suite

* **Aprobación para Merge / CI/CD:** 100% de los tests etiquetados con `@smoke` y `@positive` deben estar en verde (`PASSED`).
* **Tasa de Estabilidad (Flakiness):** La tasa de reintentos por fallas de sincronización no debe superar el 2% en 3 ejecuciones consecutivas.
